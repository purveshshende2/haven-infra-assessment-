# B0 — The `count` trap

## What `terraform plan` is

`terraform plan` is a dry run. It compares the desired configuration with the recorded state
(and, unless `-refresh=false` is used, with the real remote objects) and prints the actions
Terraform would take: create, update in place, replace (destroy and recreate), or destroy. It
does not change infrastructure. The danger in this task is that the plan is not "remove one
bucket"; it is a cascade of replacements and an unrelated destruction caused by positional
addressing.

## Reproduction

The seeded state contains four buckets at indexes `0`–`3`:

| Address | Landlord | Bucket |
|---|---|---|
| `aws_s3_bucket.landlord_media[0]` | `la-001` | `haven-media-la-001` |
| `aws_s3_bucket.landlord_media[1]` | `la-002` | `haven-media-la-002` |
| `aws_s3_bucket.landlord_media[2]` | `la-003` | `haven-media-la-003` |
| `aws_s3_bucket.landlord_media[3]` | `la-004` | `haven-media-la-004` |

Removing the middle account (`la-002`) leaves `["la-001", "la-003", "la-004"]`. `count` is
positional, so every later element moves down one index. The plan below was produced with:

```console
$ terraform plan -refresh=false -no-color \
    -var='landlord_accounts=["la-001","la-003","la-004"]'
```

The relevant output is:

```text
  # aws_s3_bucket.landlord_media[1] must be replaced
-/+ resource "aws_s3_bucket" "landlord_media" {
      ~ bucket = "haven-media-la-002" -> "haven-media-la-003" # forces replacement
      ~ tags   = {
          ~ "landlord_account_id" = "la-002" -> "la-003"
        }
    }

  # aws_s3_bucket.landlord_media[2] must be replaced
-/+ resource "aws_s3_bucket" "landlord_media" {
      ~ bucket = "haven-media-la-003" -> "haven-media-la-004" # forces replacement
      ~ tags   = {
          ~ "landlord_account_id" = "la-003" -> "la-004"
        }
    }

  # aws_s3_bucket.landlord_media[3] will be destroyed
  # (because index [3] is out of range for count)
  - resource "aws_s3_bucket" "landlord_media" {
      - bucket = "haven-media-la-004" -> null
    }

Plan: 4 to add, 0 to change, 3 to destroy.
```

The four adds are the two replacement buckets plus the two unrelated B1 resources
(`listing_media` and its lifecycle configuration) that are not yet in the seeded state. For the
B0 buckets specifically, the plan is:

* **`[1]` replaced**: the address that used to mean `la-002` now means `la-003`. The bucket
  name and the `landlord_account_id` tag change, and both force replacement.
* **`[2]` replaced**: the address that used to mean `la-003` now means `la-004`.
* **`[3]` destroyed**: there is no fourth element any more, so Terraform destroys the bucket
  that used to belong to `la-004`.

Only `[0]` (`la-001`) is untouched. In other words, removing one account from the middle
destroys or replaces the buckets of the two accounts that were *not* removed as collateral
damage.

## Why this is dangerous

1. **Data loss.** A replacement is a destroy followed by a create. S3 bucket names are unique,
   so old objects are not carried into the new bucket. If `force_destroy = true` is set,
   Terraform empties each bucket and permanently deletes every tenant document, listing photo,
   and screening artifact before recreating it. `force_destroy = true` is a convenience for
   disposable buckets, not a safe default for production media.
2. **Apply failure on non-empty buckets.** The AWS provider's default is
   `force_destroy = false`. Destroying or replacing a non-empty bucket then fails with
   `BucketNotEmpty`. Because Terraform may already have destroyed some buckets before it reaches
   the failure, the apply can stop half-finished: part of the fleet is gone, the state is
   inconsistent, and the next plan is harder to reason about. The failure does not protect the
   data that was already deleted in earlier steps.
3. **Cross-tenant IAM and output misrouting.** Anything that references a positional address
   follows the index, not the landlord. An IAM policy, bucket policy, CloudFront origin, app
   configuration value, or Terraform output such as `aws_s3_bucket.landlord_media[1].id` now
   resolves to a different landlord's bucket. A property manager for `la-003` can be pointed at
   `la-004`'s media, or vice versa, which is a cross-tenant data exposure. Cost allocation also
   drifts because the replacement bucket is tagged with the new occupant's
   `landlord_account_id`.
4. **Noisy, slow recovery.** The apparent intent was one deletion. The actual plan destroys
   healthy infrastructure, requires re-uploading data, and may require manual state surgery.
   The larger the list, the larger the blast radius: removing index `i` touches every address
   after `i`.

## The fix: key by an immutable identity, not by position

Use `for_each` with the immutable `landlord_account_id` as the key. Resource addresses become
stable names such as `aws_s3_bucket.landlord_media["la-003"]`; adding or removing another key
does not move them.

```hcl
variable "landlord_accounts" {
  type        = list(string)
  description = "Immutable landlord account IDs."
  default     = ["la-001", "la-002", "la-003", "la-004"]
}

resource "aws_s3_bucket" "landlord_media" {
  for_each = toset(var.landlord_accounts)

  bucket = "haven-media-${each.key}"

  tags = {
    landlord_account_id = each.key
  }

  # Explicit, safe default: never silently empty a production bucket.
  force_destroy = false
}
```

If the variable holds objects rather than bare IDs, build the map explicitly:

```hcl
for_each = { for account in var.landlord_accounts : account.landlord_account_id => account }
```

With that change, removing `la-002` produces exactly one destroy:
`aws_s3_bucket.landlord_media["la-002"]`. The `la-003` and `la-004` buckets keep their addresses,
names, tags, policies, and objects.

## Migrating the existing `count` state safely

Do not apply the `for_each` change on top of the old positional state without moving the
addresses first. Terraform supports `moved` blocks (preferred, reviewable in version control):

```hcl
moved {
  from = aws_s3_bucket.landlord_media[0]
  to   = aws_s3_bucket.landlord_media["la-001"]
}

moved {
  from = aws_s3_bucket.landlord_media[1]
  to   = aws_s3_bucket.landlord_media["la-002"]
}

moved {
  from = aws_s3_bucket.landlord_media[2]
  to   = aws_s3_bucket.landlord_media["la-003"]
}

moved {
  from = aws_s3_bucket.landlord_media[3]
  to   = aws_s3_bucket.landlord_media["la-004"]
}
```

Alternatively, run `terraform state mv` for each pair. Either way, verify that the plan for the
retained accounts is a no-op before doing the actual removal. For production buckets, consider
`lifecycle { prevent_destroy = true }` as a second guardrail; intentionally removing an account
then becomes a deliberate, reviewed state operation instead of an accidental side effect of
editing a list.

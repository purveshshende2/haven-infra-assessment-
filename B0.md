# B0 — The `count` trap

What does `terraform plan` show when a middle landlord account is removed from the list? Why is
that dangerous here? What's the fix?

##what `terraform plan` shows
when a landlord account is removed from the middle of the list (e.g., index `1` out of `[0,1,2]`), terraform shifts the indiced of every subsequent element (`inde 2` become `index 1`). `terraform plan` will show:

1.**In-place updates or forced replacements** (`-/+ destroy and then create replacement`) for every bucket positioned after the  deleted item because their resource addresses (`aws_s3_bucket.landlorrd[1]`) now map to different landlord / buckcet names.

2.**Destruction** of the final index (`aws_s3_bucket.landlord[2]`).

##Why it is Dangerous

* **Data Loss / Destruction Failure :** If buckets contain tenet documents or listing photos, Terraform will either fail to destroy non-empty buckets (blocking deployments) or , if `force_destroy = true` is set, **permanently delete active landlords' prodcution data**.
**Cross-Tenet Data Exposure:** If bucket names are derived without forcing replacement, or if downstream IAM policies /outputs reference list indices, Landlord C's IAM role or application config could temporily point to Landlord B's bucket.

## The Fix
Replace `count` with `for_each` keyed by a unique, immutable identifier such as `landlord_account_id` (converted to a map/set):

```hcl
resource "aws_s3_bucket" "landlord" {
    for_each = {for l in var.landlords : l.landlord_account_id => l}
    bucket = haven-landlord-${each.key}"

}

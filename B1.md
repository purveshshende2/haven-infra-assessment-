# B1 — The Glacier cost gotcha

## The timeline

| Day | Event | Storage class |
|---|---|---|
| 0 | Photo uploaded | S3 Standard |
| 30 | Lifecycle rule transitions the photo to Glacier | S3 Glacier Flexible Retrieval |
| 40 | Seller requests deletion; the application deletes immediately | Deleted |

The object spent only **10 days** in Glacier. Glacier Flexible Retrieval has a **90-day minimum
storage duration**, so the remaining **80 days** are still billable. S3 does not refuse the
delete; it charges a **prorated early deletion fee** for the part of the minimum duration the
object did not use.

## What the early deletion actually costs

For a single object, the early deletion fee is roughly:

```text
remaining days = 90 - (day_deleted - day_archived)
               = 90 - (40 - 30)
               = 80 days

early deletion fee ≈ object_size × (80 / 30) × Glacier_GB_month_price
```

At the us-east-1 Glacier Flexible Retrieval list price of roughly **$0.0036 per GB-month** (check
current pricing), each GB deleted on day 40 costs about:

```text
1 GB × (80 / 30) × $0.0036 ≈ $0.0096
```

That looks small per GB, but it is pure waste: the data is gone and the storage was barely used.
At 5 TB of listing photos, the early deletion charge alone is roughly **$48**; at 50 TB it is
roughly **$480**. The exact number depends on object size, storage class, and region.

The minimum duration differs by archive class:

* **S3 Glacier Instant Retrieval** — 90 days
* **S3 Glacier Flexible Retrieval** — 90 days
* **S3 Glacier Deep Archive** — 180 days

If the rule used Deep Archive instead, deleting on day 40 would leave **170 days** billable, not
80. The lesson is the same, but the penalty is more than twice as large.

### Costs that are charged even though the object was deleted

The early deletion fee is not the only charge:

1. **Transition request charges.** Every object transitioned to Glacier is a billable request,
   typically priced per 1,000 requests (for example, about $0.03 per 1,000 for Glacier Flexible
   Retrieval in us-east-1 at the time of writing). Transitioning one million photos costs about
   **$30 in requests alone**, even if every photo is deleted ten days later.
2. **40 KB of per-object overhead.** S3 adds 8 KB of Standard-rate metadata plus 32 KB of
   Glacier-rate index/metadata for each archived object. That overhead is billed for the minimum
   duration too. For small photos, 40 KB can be a large fraction of the object, and it can make
   Glacier more expensive than keeping the object in Standard.
3. **Restore/retrieval charges.** If the seller asks for a copy of the photos before deletion,
   archived objects are not readable in real time. You must restore a temporary copy (minutes to
   hours for Glacier Flexible Retrieval, hours for Deep Archive) and pay both the retrieval fee
   and Standard-rate storage for the restored copy while it exists.
4. **Async transition billing.** Lifecycle transitions are asynchronous. Billing at the
   destination class, including the minimum-duration clock and the 40 KB overhead, starts when
   the lifecycle rule is satisfied, even if the physical transition has not completed yet.

## The archiving impact beyond the early deletion fee

Archiving is not just a cheaper storage tier; it changes what the application can do:

* **No real-time reads.** Glacier Flexible Retrieval and Deep Archive objects must be restored
  before they can be read. A property manager or tenant trying to view a sold listing's photos
  will get an error or a long delay unless the application has a restore workflow.
* **One-way lifecycle transitions.** S3 Lifecycle can move Glacier Flexible Retrieval to Deep
  Archive, but it cannot move either class back to Standard. Going back requires a restore plus
  a copy/overwrite, which adds retrieval and request costs.
* **Small objects may not transition at all.** Since September 2024, S3's default behavior
  prevents objects smaller than **128 KB** from transitioning to any storage class unless the
  lifecycle rule explicitly opts in with an object-size filter. A rule that assumes every photo
  is archived can therefore leave many small photos in Standard while still paying for the
  transition machinery on the large ones.
* **Deletion obligations can conflict with retention.** If a seller's deletion request must be
  honored within 30 days, archiving the object before that window closes makes the deletion
  more expensive and can delay it behind a restore. The lifecycle policy and the deletion policy
  need to agree on the same retention clock.

## Redesigning the lifecycle

The core fix is simple: **do not put an object into a minimum-duration archive class until the
period in which it might be deleted has passed.** If the seller can request deletion at any
time, and deletion must complete within 30 days of the request, then the object should remain in
a class with no minimum duration until at least the end of that deletion window.

### 1. Delay the Glacier transition past the deletion window

For the stated scenario, change the transition from day 30 to day 90 (or later). The day-40
request has a deletion deadline of day 70, so the object is still in S3 Standard when it is
deleted. Standard has no minimum storage duration, so deleting it costs nothing beyond the
normal request charges.

The general rule is stronger than "always transition on day 90": transition only after the
**latest possible deletion deadline** for that object. If a seller can request deletion at any
time, a single fixed transition day is not sufficient — a request on day 70 would have a day-100
deadline, which is only ten days after a day-90 transition. In that case, keep the object in a
no-minimum class until it is no longer eligible for a deletion request, or derive the transition
date from the maximum request window and the 30-day deletion SLA. The day-90 example below is
correct for the assignment's day-40 request and for a request window that closes by day 60.

```hcl
resource "aws_s3_bucket_lifecycle_configuration" "listing_media_archive" {
  bucket = aws_s3_bucket.listing_media.id

  rule {
    id     = "archive-sold-listing-photos"
    status = "Enabled"

    filter {
      and {
        # Prefix used here for a compact example; a tag filter works too.
        prefix                   = "sold/"
        # Avoid archiving tiny objects where 40 KB of overhead and
        # per-object transition requests erase the savings.
        object_size_greater_than = 131072
      }
    }

    transition {
      days          = 90
      storage_class = "GLACIER"
    }
  }
}
```

If archive savings are still wanted between day 30 and day 90, use a class that does not impose
a 90-day minimum:

* **S3 Intelligent-Tiering** — no minimum storage duration; S3 moves objects between access
  tiers automatically. It has a per-object monitoring/automation fee, so it is best for larger
  objects rather than millions of tiny photos.
* **S3 Standard-IA** — 30-day minimum storage duration and a 128 KB minimum billable object
  size; suitable only when the object will remain in that class for at least 30 days. It does
  not protect an object that is deleted on day 40 unless the minimum is already satisfied.

The safest primary design is to keep the object in S3 Standard until the deletion window closes,
then transition it to Glacier. A two-step rule (Standard-IA at day 30, Glacier at day 90) can
work for objects that are known to be retained, but it is not a substitute for keeping the
deletion window out of the archive class.

### 2. Archive only objects that are actually sold and past the window

Use a tag or prefix to separate active listings from sold listings, and apply the archive rule
only to the sold set. If the business rule is "archive 30 days after sale," copy the object to
an `archive/` prefix at sale time (which gives it a new creation date) and transition that copy
90 days later. Do not use one blanket rule that archives every upload after 30 days.

### 3. Make deletion a workflow, not an immediate `DeleteObject`

The application should check the object's storage class and transition date before deleting:

* If the object is in Standard or another class with no minimum, delete immediately.
* If it is inside a minimum-duration window, either defer deletion until the window ends (when
  the legal/contractual deadline allows it) or explicitly accept the prorated fee.
* Queue deletion requests with a `not_before` date and process them after the minimum duration.

This makes the cost visible and intentional instead of a silent line item.

### 4. Monitor the fee

Tag archive objects with `landlord_account_id` and the listing/sale identifier, enable S3
Lifecycle Event Notifications, and track early-deletion fees in Cost Explorer or a CUR query.
A budget alarm on the Glacier cost category will surface a bad transition rule before it scales.

## Why the original rule is the root cause

The original rule optimizes for the earliest possible archive date, not for the deletion
contract. It moves an object into a 90-day-minimum class at day 30, while the business still
allows deletion requests through day 70 (30 days after a day-40 request). The two policies are
incompatible. Delaying the transition until after the deletion window removes the early deletion
fee entirely; it also avoids paying transition requests and 40 KB of overhead for objects that
were only going to live another ten days.
